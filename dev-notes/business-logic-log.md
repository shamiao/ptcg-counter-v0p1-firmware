## 步骤 1：20ms 时间片内核（timeslice 模块）+ UART 演示

日期：2026-09-28　构建：data=40.1 xdata=6 const=8 code=2457，0 错 0 警

### 硬件事实（决定性约束）

**STC8H 的 WKT 没有 中断向量。** STC8H.H 向量表（INT0…TMR11）中无 WKT；手册 7.11 节
例程是纯唤醒用法（`PCON=0x02` 后顺序执行，无 ISR、无标志位、无 IE 使能位）。

因此用户方案"WKT 中断时 cycle+1"做等价变换：**`PCON|=0x02` 睡下，醒来后的第一条
语句 `g_cycle++`**——"从 STOP 醒来"就是本芯片上的 WKT 事件。推论（设计契约）：

- **醒着的时候时间不走**：某片工作超过 20ms 时，错过的 WKT 溢出不可观测，tick 静默
  丢失（时间变慢），而不是排队。业务代码禁止阻塞超过一个时间片。
- 全固件目前**没有任何中断源**（EA=0），g_cycle/g_cycle_main 均只被主流程顺序访问，
  16 位读改写不存在撕裂/竞态问题。
- 未来若加 INT0（KEY_MAIN）唤醒：醒来后必须先区分唤醒源（INT0 标志/引脚电平），
  按键唤醒不是 tick，不能 cycle++，处理完应继续睡完本片。

### WKT 配置

- 计数时钟 = 32kHz/16 = **2kHz**（0.5ms/格），周期 = (N+1)×0.5ms。手册 6 行样例全部
  吻合（N=9→5ms、999→0.5s、7FF→约 1s/1.024s）。
- 20ms → N=39：`WKTCL=0x27, WKTCH=0x80`（WKTEN）。
- WKT 精度受 32kHz IRC 漂移限制（手册提及其校准值在 idata F8/F9，本应用不需要）。
- `IRCDB=0x10`（XFR 0xFE06，需 EAXFR）：掉电唤醒 IRC 防扰滤波，手册 7.3.8 指出不配
  会让 CPU 唤醒瞬间跑飞数个周期，必须设。

### 回绕保护

g_cycle_main ≤ g_cycle 恒成立（主循环只在落后时 +1，且本实现 lag ≤ 1）。任一变量越过
0x8000 时把公共值（=g_cycle_main）从两者中减掉：差值保留、基数归零，u16 永不回绕。

### UART 演示（发布前移除 printf）

每处理 50 片打印 `ts %u`（片计数 50、100、…），50×20ms=1s，终端应看到约 1 行/秒。
约束：

- 9600 8N1 下一行 ≤~10 字符 ≈ 10ms，占 20ms 片的一半——printf 只允许出现在少数片中，
  行长加长前先算这笔账；
- 打印后 `DelayMs(1)`：TI 在停止位开始时置位，直接 STOP 会停掉 UART 时钟截断停止位；
- printf 链入成本：骨架 1276 → 2457（约 +1.2KB，见 firmware-conventions.md）。

### 烧录注意

- **不要在 STC-ISP 里启用硬件看门狗**：WDT 会把 STOP 打断成复位（当前未启用）。
- 其余照旧：IRC 6MHz，9600 8N1。

### 台架验收

串口应每秒稳定出现一行递增的 `ts N`；用秒表对比 N 与真实秒数可估 WKT 实际偏差
（32kHz IRC 允许百分级误差）。

### 修订（用户决策，同日）：单 cycle 帧循环

用户确认"醒着时间不走"的语义后拍板：**去掉 cycle_main 和 rebase，只留一个
g_cycle**。模型即游戏机帧循环——干活、睡一个 WKT 周期、醒来 cycle+1。超片表现为
**掉帧/lag**（该片被拉长到下一个 WKT 溢出，无积压），可接受，因为业务负载远低于
20ms/片。主循环不再有比较分支，直接 `工作 → Slice_SleepOneTick()`。

- g_cycle 自然回绕（65536 片 ≈ 21.8 分钟），业务要更长时长自带计数器；
- 单线程无竞态的论证不变（全固件无中断源）；
- 构建变为 data=38.1 xdata=6 code=2395。

## 步骤 2：WKT 频率校准 EarlyInit（用户指令，同日）

日期：2026-09-28　构建：data=39.1 xdata=10 const=28 code=2551，0 错 0 警

### 手册 7.11.1 的权威事实（PDF 原文核对，temp/ch5-full.txt 行 7807-7808）

- WKT 用**自带 ~32kHz RC 振荡器**，手册原话"误差较大"，出厂记录的实际频率镜像在
  **idata F8H/F9H（大端，单位 Hz）**。
- 公式：`定时(µs) = 10⁶ × 16 × 计数次数 / Fwt`，寄存器写"计数次数−1"；**0 和 32767
  为保留值**，可用上限 32766。
- 附带发现：唤醒后"可读 WKTCH/WKTCL 获取睡眠时间"（按重装值+Fwt 换算，非实时计数）。
- **勘误**：此前 vlcd.c 注释与约定文档称"F8/F9 为 24M IRC 校准"——手册全文检索无任何
  佐证（"24M"命中皆为 PLL 相关），F8/F9 的唯一出处就是 7.11.1 的 WKT 频率。已修正注释。

### 实现（timeslice 模块）

`Timeslice_EarlyInit()` 挂在 main 第二句（VLCD_EarlyInit 之后、UART 之前，同样赶在
栈增长前抢读高 idata）：

1. 快照 idata F8/F9 → `g_fwt_hz`（xdata，原始值留作报告）；
2. 合法窗口 **24000–40000 Hz**，越界（含填充 0x0000/0xFFFF/0xD3D3 等）→ 回退标称
   32000（与 BGV 的 1000–1400→1190 同款失效安全）；
3. `count = round(Fwt × SLICE_MS / 16000)`（u32 乘加除，+8000 四舍五入），重装值 =
   count−1 存 `g_wkt_reload`；`Timeslice_Init()` 直接写入 WKTCL/WKTCH（拼 WKTEN）。

开机报告一行 `wkt fwt=<raw> cnt=<ticks/slice>`（打印在 Timeslice_Init 之前，属线性
boot 段不受 20ms 片约束），用于台架核对镜像是否读得像话；fwt=32000 且 cnt=40 即回退
路径生效的标志。

### 精度极限（勿期望过高）

- 校准消掉的是 RC 静态频偏；剩余误差 = **0.5ms 计数格量化**（四舍五入后每片确定性
  偏差 ≤±0.25ms，即 ±1.25% 稳定速率差）+ 温漂。1s 打印节奏预期准到百分级。
- 若未来要更好：可按片抖动 count（41/42 交替）做分数分频，暂不做。

### 步骤 2 补充勘误（用户质疑 vlcd.c 注释引出，同日）

用户指出 vlcd.c 头注释提 IRC 频率离谱。核查结论：**vlcd.c 功能代码从不碰 IRC**（功能链
仅 BGV→ADC15 反推 VCC→PWM 占空比），IRC 字样纯属注释里顺带描述 idata 镜像区"街坊"，
属注释职责错位。顺藤查手册（temp/ch5-full.txt）又纠出两处真错并已修：

1. **"0xF1-0xF7 = 32K IRC trim" 查无出处**：手册全文无 idata F1-F7 的任何描述
   （10.4 章 CHIP 表只讲 XDATA 0xFDE0 区）。该说法是上会话从残缺文本的误读。
2. **WKT 标称值应为 32768 而非 32000**：10.4.3 明示 32K 掉电唤醒定时器频率标准值
   8000H=32768Hz（7.11.1 的"约 32KHz"即此）。`FWT_NOMINAL_HZ` 已改 32768（回退路径
   count=41，周期 20.008ms）。
3. **10.4.3 交叉佐证 F8/F9**：XDATA CHIPID9/10（FDE9/FDEA）= 同一个 WKT 频率字
   （该 xdata 区在本片实测为固定填充，不可用，idata 镜像才是活路——与 BGV 排障结论
   一致）。

整改：镜像区完整地图移入 hardware-definition.h（芯片级事实归芯片级文件），vlcd.c 注释
只留 BGV 自身+指针；构建不变（data=39.1 xdata=10 code=2551）。另：源码注释一律英文
（"误差较大"→"wide tolerance"、"反推VCC"→"reverse-VCC"），全工程 .c/.h 已零中文。

## 步骤 4：段码显示（display 模块 + 自检显示，用户指令，同日）

日期：2026-09-28　构建：data=42.1 xdata=10 const=247 code=2799，0 错 0 警

### 架构（用户设计，含一次中途修订）

- **显示缓冲区** `g_disp_buf[3]`（data）：[0]=个位 [1]=十位 [2]=百位（从右到左）。
  bit0~5=字符码 0~35（'0'~'9','A'~'Z'，>35 熄灭），bit6=小数点（个位无 DP，忽略），
  bit7=使能。**DP 与使能独立**：熄灭位仍可单点小数点。
- **查表**（code 区 `g_7segtab[3][36][2]`，216B）：每位置×每字符 2 字节
  {segX, segY} = 该字形两个 nibble 的直接内容。**中途修订**：原设计为
  AND 掩码+OR 叠加（读改写式），用户改为**全面覆写**——掩码取消、只存数据码，
  渲染从 00h 起拼 6 个 nibble 一次写入。三位置条目内容相同（接线均匀）仍各存
  一份：免运行时换算，也为非均匀接线留余地。
- **接线**（hardware-definition.h）：每位数字占两个 SEG nibble；segX=COM0/1/2/3 对应
  A/B/F/G，segY 对应 C/D/E/DP（个位 segY 的 bit3 为 NC）。DP=缓冲区 bit6 直控
  segY bit3。
- **字形**：严格按 [7seg-charset.html](7seg-charset.html)；K/M/V/W/X 兜底为 "_"（仅亮
  d）；S=5、Z=2 同形；6 带顶横、9 带底横（底横省略形分给 Q）。

### 生成工具 tools/gen7segtab.py

- 字形定义以代码形式内嵌（FONT 字典，含每个特殊形的中文注释），改字形只动脚本
  重跑；脚本注释充分，输出的查表按约定**零注释**。
- 校验摘要走 stderr（stdout 纯 C），含位置接线、表大小、抽查点（0/1/8/K）。
- 数据来源两处：7seg-charset.html（字形）+ hardware-definition.h（接线），改任一须重跑。

### 新增原语（ht1621.c）

- `HT1621_LcdOn()`：BIAS 1/3 4COM(0x29) + LCD_ON(0x03)——常规显示路径用，
  与诊断用的 AllSegmentsOn 分开。
- `HT1621_WriteRam(addr, src, n)`：WRITE 突发（"101"+地址 MSB-first+n 个 nibble
  LSB-first，地址自增）。带 out 的 RMW 只留在诊断函数里。

### 自检流程（main.c，仍为线性延时式）

SysInit → LcdOn → 写缓冲 {8, 8., 8.} 渲染 → boot 报告（wkt fwt/cnt，打印泡在
1s 窗口里，UART 自然排空）→ `DelayMs(1000)` → 缓冲清零渲染（LCD 保持 ON，自检
结束）→ Timeslice_Init → 写 {0, 灭, 灭} 渲染（"空空0"）→ 进入帧循环（ts 演示不变）。

### 台架验收

上电应看到：8.8.8 全亮 1 秒 → 熄灭 → 右侧单独一个"0"；期间串口有 wkt 校准行、
之后每秒一行 ts N。若某段接错，8.8.8 阶段即可目视定位（与旧 AllSegmentsOn 等效）。

### 步骤 4 勘误：HT1621 数据位序是 MSB-first（台架实锤，同日）

**现象**（用户报告）：自检 8.8.8 正常，业务态"空空0"的 0 显示成不成字的 bdefg。

**解码**：'0' 的两个 nibble 均为 0x07，按 D0-first 发出后被芯片锁存为 0x0E——
首位数据落进 D3。发 6 个 1 只亮 5 段、缺的那段恰好落在唯一 NC（个位 DP 位），
与"每 nibble 反相"完全吻合；8.8.8 阶段全 0x0F 位序不敏感所以自检无异常
（bring-up 期的 RMW 诊断写读也全是 0x0F，**位序从未被验证过**）。

**佐证**：edholmes2232/ht1621 经典驱动源码数据 nibble 按 MSB-first 打包；手册
时序图标注 "D0 D1 D2 D3" 是著名陷阱（上会话把标注当线上顺序记进了约定）。
结论：**HT1621 总线所有字段（mode/地址/命令/数据）一律 MSB-first**。

**修复**：`HT1621_WriteRam`、AllSegmentsOn 的 RMW 读写、`HT1621_ReadDump` 的读取
全部改为 MSB-first（后两者虽是诊断路径，明知错序留着必坑后人）。构建
data=42.1 xdata=10 const=247 code=2804。

教训记入：手册图的位标注 ≠ 线上顺序；诊断数据要含非对称图案才能验位序。
