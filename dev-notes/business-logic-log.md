## 步骤 1：20ms 时间片内核（timeslice 模块）+ UART 演示

日期：2026-09-28　构建：data=40.1 xdata=6 const=8 code=2457，0 错 0 警

### 硬件事实（决定性约束）

**STC8H 的 WKT 没有 中断向量。** STC8H.H 向量表（INT0…TMR11）中无 WKT；手册 7.11 节
例程是纯唤醒用法（`PCON=0x02` 后顺序执行，无 ISR、无标志位、无 IE 使能位）。

因此用户方案"WKT 中断时 cycle+1"做等价变换：**`PCON|=0x02` 睡下，醒来后的第一条
语句 `g_cycle++`**——"从 STOP 醒来"就是本芯片上的 WKT 事件。推论（设计契约）：

- **醒着的时候时间不走**：某片工作超过 20ms 时，错过的 WKT 溢出不可观测，tick 静默
  丢失（时间变慢），而不是排队。业务代码禁止阻塞超过一个时间片。
- 全固件目前**没有任何中断源**（EA=0），g_cycle/g_cycle_main 均只被主流程顺序访问，
  16 位读改写不存在撕裂/竞态问题。
- 未来若加 INT0（KEY_MAIN）唤醒：醒来后必须先区分唤醒源（INT0 标志/引脚电平），
  按键唤醒不是 tick，不能 cycle++，处理完应继续睡完本片。

### WKT 配置

- 计数时钟 = 32kHz/16 = **2kHz**（0.5ms/格），周期 = (N+1)×0.5ms。手册 6 行样例全部
  吻合（N=9→5ms、999→0.5s、7FF→约 1s/1.024s）。
- 20ms → N=39：`WKTCL=0x27, WKTCH=0x80`（WKTEN）。
- WKT 精度受 32kHz IRC 漂移限制（手册提及其校准值在 idata F8/F9，本应用不需要）。
- `IRCDB=0x10`（XFR 0xFE06，需 EAXFR）：掉电唤醒 IRC 防扰滤波，手册 7.3.8 指出不配
  会让 CPU 唤醒瞬间跑飞数个周期，必须设。

### 回绕保护

g_cycle_main ≤ g_cycle 恒成立（主循环只在落后时 +1，且本实现 lag ≤ 1）。任一变量越过
0x8000 时把公共值（=g_cycle_main）从两者中减掉：差值保留、基数归零，u16 永不回绕。

### UART 演示（发布前移除 printf）

每处理 50 片打印 `ts %u`（片计数 50、100、…），50×20ms=1s，终端应看到约 1 行/秒。
约束：

- 9600 8N1 下一行 ≤~10 字符 ≈ 10ms，占 20ms 片的一半——printf 只允许出现在少数片中，
  行长加长前先算这笔账；
- 打印后 `DelayMs(1)`：TI 在停止位开始时置位，直接 STOP 会停掉 UART 时钟截断停止位；
- printf 链入成本：骨架 1276 → 2457（约 +1.2KB，见 firmware-conventions.md）。

### 烧录注意

- **不要在 STC-ISP 里启用硬件看门狗**：WDT 会把 STOP 打断成复位（当前未启用）。
- 其余照旧：IRC 6MHz，9600 8N1。

### 台架验收

串口应每秒稳定出现一行递增的 `ts N`；用秒表对比 N 与真实秒数可估 WKT 实际偏差
（32kHz IRC 允许百分级误差）。

### 修订（用户决策，同日）：单 cycle 帧循环

用户确认"醒着时间不走"的语义后拍板：**去掉 cycle_main 和 rebase，只留一个
g_cycle**。模型即游戏机帧循环——干活、睡一个 WKT 周期、醒来 cycle+1。超片表现为
**掉帧/lag**（该片被拉长到下一个 WKT 溢出，无积压），可接受，因为业务负载远低于
20ms/片。主循环不再有比较分支，直接 `工作 → Slice_SleepOneTick()`。

- g_cycle 自然回绕（65536 片 ≈ 21.8 分钟），业务要更长时长自带计数器；
- 单线程无竞态的论证不变（全固件无中断源）；
- 构建变为 data=38.1 xdata=6 code=2395。

## 步骤 2：WKT 频率校准 EarlyInit（用户指令，同日）

日期：2026-09-28　构建：data=39.1 xdata=10 const=28 code=2551，0 错 0 警

### 手册 7.11.1 的权威事实（PDF 原文核对，temp/ch5-full.txt 行 7807-7808）

- WKT 用**自带 ~32kHz RC 振荡器**，手册原话"误差较大"，出厂记录的实际频率镜像在
  **idata F8H/F9H（大端，单位 Hz）**。
- 公式：`定时(µs) = 10⁶ × 16 × 计数次数 / Fwt`，寄存器写"计数次数−1"；**0 和 32767
  为保留值**，可用上限 32766。
- 附带发现：唤醒后"可读 WKTCH/WKTCL 获取睡眠时间"（按重装值+Fwt 换算，非实时计数）。
- **勘误**：此前 vlcd.c 注释与约定文档称"F8/F9 为 24M IRC 校准"——手册全文检索无任何
  佐证（"24M"命中皆为 PLL 相关），F8/F9 的唯一出处就是 7.11.1 的 WKT 频率。已修正注释。

### 实现（timeslice 模块）

`Timeslice_EarlyInit()` 挂在 main 第二句（VLCD_EarlyInit 之后、UART 之前，同样赶在
栈增长前抢读高 idata）：

1. 快照 idata F8/F9 → `g_fwt_hz`（xdata，原始值留作报告）；
2. 合法窗口 **24000–40000 Hz**，越界（含填充 0x0000/0xFFFF/0xD3D3 等）→ 回退标称
   32000（与 BGV 的 1000–1400→1190 同款失效安全）；
3. `count = round(Fwt × SLICE_MS / 16000)`（u32 乘加除，+8000 四舍五入），重装值 =
   count−1 存 `g_wkt_reload`；`Timeslice_Init()` 直接写入 WKTCL/WKTCH（拼 WKTEN）。

开机报告一行 `wkt fwt=<raw> cnt=<ticks/slice>`（打印在 Timeslice_Init 之前，属线性
boot 段不受 20ms 片约束），用于台架核对镜像是否读得像话；fwt=32000 且 cnt=40 即回退
路径生效的标志。

### 精度极限（勿期望过高）

- 校准消掉的是 RC 静态频偏；剩余误差 = **0.5ms 计数格量化**（四舍五入后每片确定性
  偏差 ≤±0.25ms，即 ±1.25% 稳定速率差）+ 温漂。1s 打印节奏预期准到百分级。
- 若未来要更好：可按片抖动 count（41/42 交替）做分数分频，暂不做。

### 步骤 2 补充勘误（用户质疑 vlcd.c 注释引出，同日）

用户指出 vlcd.c 头注释提 IRC 频率离谱。核查结论：**vlcd.c 功能代码从不碰 IRC**（功能链
仅 BGV→ADC15 反推 VCC→PWM 占空比），IRC 字样纯属注释里顺带描述 idata 镜像区"街坊"，
属注释职责错位。顺藤查手册（temp/ch5-full.txt）又纠出两处真错并已修：

1. **"0xF1-0xF7 = 32K IRC trim" 查无出处**：手册全文无 idata F1-F7 的任何描述
   （10.4 章 CHIP 表只讲 XDATA 0xFDE0 区）。该说法是上会话从残缺文本的误读。
2. **WKT 标称值应为 32768 而非 32000**：10.4.3 明示 32K 掉电唤醒定时器频率标准值
   8000H=32768Hz（7.11.1 的"约 32KHz"即此）。`FWT_NOMINAL_HZ` 已改 32768（回退路径
   count=41，周期 20.008ms）。
3. **10.4.3 交叉佐证 F8/F9**：XDATA CHIPID9/10（FDE9/FDEA）= 同一个 WKT 频率字
   （该 xdata 区在本片实测为固定填充，不可用，idata 镜像才是活路——与 BGV 排障结论
   一致）。

整改：镜像区完整地图移入 hardware-definition.h（芯片级事实归芯片级文件），vlcd.c 注释

（"误差较大"→"wide tolerance"、"反推VCC"→"reverse-VCC"），全工程 .c/.h 已零中文。

## 步骤 4：段码显示（display 模块 + 自检显示，用户指令，同日）

日期：2026-09-28　构建：data=42.1 xdata=10 const=247 code=2799，0 错 0 警

### 架构（用户设计，含一次中途修订）

- **显示缓冲区** `g_disp_buf[3]`（data）：[0]=个位 [1]=十位 [2]=百位（从右到左）。
  bit0~5=字符码 0~35（'0'~'9','A'~'Z'，>35 熄灭），bit6=小数点（个位无 DP，忽略），
  bit7=使能。**DP 与使能独立**：熄灭位仍可单点小数点。
- **查表**（code 区 `g_7segtab[3][36][2]`，216B）：每位置×每字符 2 字节
  {segX, segY} = 该字形两个 nibble 的直接内容。**中途修订**：原设计为
  AND 掩码+OR 叠加（读改写式），用户改为**全面覆写**——掩码取消、只存数据码，
  渲染从 00h 起拼 6 个 nibble 一次写入。三位置条目内容相同（接线均匀）仍各存
  一份：免运行时换算，也为非均匀接线留余地。
- **接线**（hardware-definition.h）：每位数字占两个 SEG nibble；segX=COM0/1/2/3 对应
  A/B/F/G，segY 对应 C/D/E/DP（个位 segY 的 bit3 为 NC）。DP=缓冲区 bit6 直控
  segY bit3。
- **字形**：严格按 [7seg-charset.html](7seg-charset.html)；K/M/V/W/X 兜底为 "_"（仅亮
  d）；S=5、Z=2 同形；6 带顶横、9 带底横（底横省略形分给 Q）。

### 生成工具 tools/gen7segtab.py

- 字形定义以代码形式内嵌（FONT 字典，含每个特殊形的中文注释），改字形只动脚本
  重跑；脚本注释充分，输出的查表按约定**零注释**。
- 校验摘要走 stderr（stdout 纯 C），含位置接线、表大小、抽查点（0/1/8/K）。
- 数据来源两处：7seg-charset.html（字形）+ hardware-definition.h（接线），改任一须重跑。

### 新增原语（ht1621.c）

- `HT1621_LcdOn()`：BIAS 1/3 4COM(0x29) + LCD_ON(0x03)——常规显示路径用，
  与诊断用的 AllSegmentsOn 分开。
- `HT1621_WriteRam(addr, src, n)`：WRITE 突发（"101"+地址 MSB-first+n 个 nibble
  LSB-first，地址自增）。带 out 的 RMW 只留在诊断函数里。

SysInit → LcdOn → 写缓冲 {8, 8., 8.} 渲染 → boot 报告（wkt fwt/cnt，打印泡在

### 步骤 4 勘误：HT1621 数据位序是 MSB-first（台架实锤，同日）

**现象**（用户报告）：自检 8.8.8 正常，业务态"空空0"的 0 显示成不成字的 bdefg。

**解码**：'0' 的两个 nibble 均为 0x07，按 D0-first 发出后被芯片锁存为 0x0E——
首位数据落进 D3。发 6 个 1 只亮 5 段、缺的那段恰好落在唯一 NC（个位 DP 位），
与"每 nibble 反相"完全吻合；8.8.8 阶段全 0x0F 位序不敏感所以自检无异常
（bring-up 期的 RMW 诊断写读也全是 0x0F，**位序从未被验证过**）。

**佐证**：edholmes2232/ht1621 经典驱动源码数据 nibble 按 MSB-first 打包；手册
时序图标注 "D0 D1 D2 D3" 是著名陷阱（上会话把标注当线上顺序记进了约定）。
结论：**HT1621 总线所有字段（mode/地址/命令/数据）一律 MSB-first**。

**修复**：`HT1621_WriteRam`、AllSegmentsOn 的 RMW 读写、`HT1621_ReadDump` 的读取
全部改为 MSB-first（后两者虽是诊断路径，明知错序留着必坑后人）。构建
data=42.1 xdata=10 const=247 code=2804。

教训记入：手册图的位标注 ≠ 线上顺序；诊断数据要含非对称图案才能验位序。

## 步骤 6：按键状态机（用户设计，核心业务逻辑起点）

日期：2026-09-28　构建：data=44.1 xdata=10 const=257 code=2936，0 错 0 警（+64 code / +2 data）

用户设计（四条规则，原样实现）：

1. 开机恒为 S0（按住键开机也是 S0，简单处理）；
2. S0 →（按下 1 键）→ S1，**触发一次**按键逻辑（沿触发，无自动重复）；
3. 任意态 →（2+ 键同按）→ S2，无效拦截；
4. S1/S2 →（全松，键数归 0）→ S0。

### 设计评估（为什么成立）

- **20ms 采样节拍本身就是消抖器**：一次采样只看瞬时快照，触点抖动（典型
  闭合 1~5ms、断开 ≤10ms）短于一片就永远落不到采样点上——不需要独立的
  计数器/积分器式消抖。
- **每片原子分类**：一个样本被不可细分地归类为 0 / 恰好 1 / ≥2 键
  （`mask & (mask-1)` 判 ≥2）。两键在首个能看见它们的采样点之前都已按下，
  该样本直接读 2+ → S2，**不可能泄漏出单键事件**；若 A 先稳定超过一片、
  B 后加入，A 触发一次后 B 的加入走 S1→S2，同样无第二次触发。
- **S1 无需记忆键身份**：换键必然经过 ≥2（→S2）或 0（→S0），物理上绕不开。
- **S2 必须全松才解锁**：顺手挡掉手指滚键（rollover）；代价是快速换键
  （未松完旧键就按新键）也会被拦——单拇指计数器场景可接受，属设计选择。
- 触发延迟 ≤1 片（20ms）+ µs 级扫描，远低于人手感知阈值（~50-100ms）。

### 已知边界（有意接受 / 暂不做）

- **按住开机**：S0 起始 + 首片采样 → 该键会触发一次。这是"简单处理"的
  直接推论，接受。
- **双触发条件**：某键在按住期间抖开 >20ms 且恰好跨过采样点，才可能
  S1→S0→S1 双触发——典型键抖远小于 20ms，属坏开关范畴。加固选项
  （新状态需连续 2 片一致才生效，+20ms 延迟、+1 字节）保留未用，实测
  双触发再启。与《AVR 单片机嵌入式系统原理与应用实践（第2版）》9.2.2
  三态确认方案的完整对比分析（为何 20ms 片下不必默认采用、启用判据、
  片长改 10ms 时的依赖关系）存档于
  [key-debounce-analysis.md](key-debounce-analysis.md)。

### 实现

- `Buttons_Scan()`（buttons.c，每片调用一次）：静态 `key_fsm`（1 字节 data），
  S0/S1/S2 三态；返回**被接受的单键掩码**（0=无事件），键逻辑在调用方分发。
  S2 释放到剩 1 键仍保持拦截（必须归零），同键持续按住不重复触发。
- main.c 帧循环：撤下已验收的字符集轮播，改为每片 `Buttons_Scan()`；
  接受事件 → 掩码转键号（KEY_MAIN=0，KEY1..6=1..6）显示在个位 + 开发期
  打印 `key N`（打印后 DelayMs(1) 再 STOP，同 ts 心跳规矩）；每秒 `ts N`
  心跳保留作节拍互证。自检后屏保持全灭，首个接受事件才点亮个位。

### 台架验收（逐条对应四规则）

1. 单按 KEY1..6：屏个位显示 1..6、串口 `key 1..6`；**按住不放只来一次**。
   KEY_MAIN：显示 0、串口 `key 0`。
2. 按住 KEY1（触发）→ 再按 KEY3：无事件；松 KEY1（KEY3 仍按）：无事件
   （S2 剩 1 键仍拦）；全松后再单按 KEY3：正常触发。
3. 两键尽量同按（<20ms 内）：从头到尾无任何事件，全松后恢复。
4. 按住任意键上电：自检后立刻触发一次该键。
5. 全程每秒一行 `ts N` 心跳不断。

## 步骤 7：KEY0 双事件与双状态机（用户设计）

日期：2026-09-28　构建：data=45.1 xdata=10 const=267 code=2992，0 错 0 警
（+56 code / +1 data / +10 const）

### 需求（用户提出）

KEY0（=KEY_MAIN，键号 0，P3.2）需支持**按下 + 松开两个事件**；并照顾多按
拦截态：若多按序列最初的按键是 KEY0（即出现过 KEY0 按下事件），则 S2 期间
只要 KEY0 松开（其他键还没松）也要**立刻触发一次 KEY0 松开事件**，但主状态
机保持 S2 继续等其他键全松。松开事件显示在 LCD 高位（百位）。

### 设计决断：双状态机（用户提议，分析确认）

用户方向：主状态机不动，为 KEY0 单搞一套只跟踪松开。分析后精确化为
**"主 FSM + 1-bit 跟踪器"**（armed/unarmed 两态），理由：

- **两个维度正交**：主 FSM 回答"全键盘键数分类"（0/1/≥2，每片原子判定，
  必须保持纯键数驱动）；"被接受的 KEY0 按下结束了吗"是独立的一维观测。
  塞进一个 FSM = 状态空间二维乘积。
- **单状态机的具体代价**：S2 转移条件从纯"键数归 0"变为"键数归 0 **或**
  （armed 且 KEY0 电平松开）"，原子分类性质被破坏；armed 要在
  S0→S1/S1→S0/S2 三处维护；两个事件通道混进一个返回值。
- **双状态机的全部代价**：`k0_armed` 1 字节 + `Buttons_Key0Released()`
  6 行 C（直接读 P3.2 电平）。
- **唯一耦合线**：主 FSM 在"接受 KEY0 按下"的边沿（S0→S1 且键为 KEY0）
  置 `k0_armed=1`。这条线保证 S2 里乱按 KEY0 不会重新武装；最初按键
  不是 KEY0 的多按（如先按 KEY3 再加按 KEY0）从未武装，其 KEY0 松开
  自然不触发。

### 实现语义细则（走查确认）

- 松开事件与被接受的按下**严格一对一**：armed 只在接受边沿置位、只在
  触发时清零；S1 正常全松路径同样触发（同一片内 Scan 回 S0、
  Key0Released 发事件）。
- armed 可跨越"S2 剩 KEY0 单键"段：主 FSM 卡 S2（全松才复位），跟踪器
  继续等 KEY0 松开，触发后 armed 清零，主 FSM 仍在 S2。
- S2 内 KEY0 重新按下再松开：无按下事件（主 FSM 在 S2 不触发）、无
  松开事件（未武装）。
- main.c：按下事件显示个位键号 + `key N`；KEY0 松开事件显示百位"0"
  + `key0 up`（两者独立位，可同屏共存）。

### 台架验收

1. 单按 KEY0：按下个位显 0 + `key 0`；松开百位显 0 + `key0 up`。
   按住不放只一对事件，快速按放各只一次。
2. 按住 KEY0 → 加按 KEY3：无新事件；松 KEY0（KEY3 仍按住）：百位 0 +
   `key0 up`（主状态仍锁 S2）；松 KEY3：回 S0，之后单按正常。
3. 按住 KEY3 → 加按 KEY0 → 松 KEY0（KEY3 仍按）：**全程无任何事件**
   （未武装）；全松后恢复。
4. 在 3 之后的 S2 内再按放 KEY0：无事件。

**台架确认（2026-09-28，用户实测）**：序列 `0↓ → 1↓ → 0↑ → 0↓ → 0↑ → 1↑`
中，前三个事件如预期触发，**后半段的 0↓/0↑ 均未触发**。机理：0↓ 被主 FSM
挡下（按下事件只在 S0→S1 边产生，S2 内该边不可达）；0↑ 被跟踪器挡下（首个
0↑ 已解除武装，重新武装的唯一入口是被接受的按下边沿——即上一件不可能发生
的事）。若跟踪器按引脚电平武装而非按"接受边沿"武装，第二个 0↑ 就会误触发
——此实测反证了唯一耦合线设计的必要性。

## 步骤 8：HP 计数核心业务（用户指令）

日期：2026-09-28　构建：data=47.1 xdata=10 const=266 code=3111，0 错 0 警
（+119 code / +2 data）

### 业务规格（用户提出）

0~990 的 HP 计数器，饱和不回绕（到底/到顶不动）。按键：1=+100、2=+10、
3=+10、4=-100、5=-10、6=-10（HP）。±10 双键是**故意的**——PTCG 血量单位
是 10，且手持设备上拇指可达性优先。±10 需带进位/退位。

### 设计决策

- **内部按"十"计数**：`count_tens`（u8，0..99）= HP/10。上界 99 恰好卡满
  3 位屏（990），u8 无溢出；PTCG 血量本就是 10 的倍数，单位天然对齐。
  按键映射：±100 → ±10 个十；±10 → ±1 个十。
- **进位/退位零成本**：每次按键后从头重算三位数字（百位=t/10、十位=t%10、
  个位恒 0），90↔100 的跨位自然正确——不做 BCD 运算，无进位 bug 面。
- **饱和**：各分支先判边界再动（如 +100：t>89 → 99；-100：t<10 → 0），
  永不回绕、永不下溢。
- **显示规则**：前导零消隐（t<10 百位灭），零显示 "  0"，个位恒 0。
- **KEY0**：按下/松开事件照常产生（步骤 7 机制不动），但业务动作待定，
  显示权归计数器——KEY0 事件不再改屏，只留开发期打印（k0/k0u）。

### 实现（main.c）

- `Counter_ApplyKey(mask)`：switch 六键映射 + 饱和；KEY0 落 default（待定）。
- `Counter_Render()`：t → 三位缓冲 + 消隐规则 + `Display_Render()`。
- 帧循环：接受事件 → ApplyKey → Render → 打印 `k<键号> v<值>0`（值以 HP
  显示，如 k2 v350；行 ~11 字符 ≈ 11ms，片预算内）。KEY0 松开打印 k0u。
- 开机 Timeslice_Init 后即渲染 "  0"（计数器待机态，不再是按键前全灭）。

### 台架验收

1. 开机自检（8.8.8+蜂鸣 0.8s → 灭 0.5s）后显示 **"  0"**。
2. KEY2/KEY3：每按 +10——0→10→…→90→**100**（进位：百位出 1、十位归 0）。
3. KEY5/KEY6：-10——100→**90**（退位：百位消隐、十位 9）。
4. KEY1/KEY4：±100——90+100→190；950+100→990；100-100→"  0"。
5. 饱和：990 上按 +10/+100 屏不动、串口值不变 v990；0 上按 -10/-100 不动。
6. 中途钳位：95+100 → 990（不是 1050 也不是回绕）。
7. 多按拦截/KEY0 事件行为与步骤 6/7 一致（显示归计数器所有）。
8. 每秒 `ts N` 心跳不断；串口值与屏显一致。

### 步骤 8 修订：u16 纯单位计数 + 术语约定（用户指令，同日）

用户三点修正：

1. **不得按"十"计数**：将来可能有"设置步长"功能（步长 10 或 1），内部
   表示必须与步长解耦。
2. **文档术语**：计数对象一律称 **DMG**——PTCG 中角色身上的数字是**已受
   伤害值**，不是血量。
3. **代码注释**：HP/DMG 都不出现——固件视角这只是一个纯计数器。

### 表示重选：u16（否决双 u8/BCD）

- **u16 纯单位计数**（采纳）：`count_val`（u16，0..990）。8051/C51 对 16 位
  加减是原生双字节指令链；饱和判断干净——加法最大 990+100=1090 不溢出，
  事后钳位即可；减法先判后减无下溢。步长 100/10/1 均匀适用，将来设置步长
  零成本切入。
- **双 u8（百位十位/个位，BCD 变体）**（否决）：每次加减都要手写跨字节
  进位/退位——把"进位需求"从渲染性质变成显式算法，正是 bug 面；且步长 1
  时个位也要进位链，复杂度只增不减。
- 显示取位：百位 v/100、十位 (v/10)%10、个位 v%10，每次重算（C51 常数除
  法优化为乘移位，代价小）；消隐规则改为标准前导零消隐：百位亮当 v≥100、
  十位亮当 v≥10、个位恒亮。当前步长（100/10）下个位实际恒 0，但表示上
  不再假设。
- 构建：data=49.1 xdata=10 const=264 code=3299（+188 code / +2 data）。
- 代码注释已全部中性化（"saturating counter"，无 HP/DMG 字样）；本文档
  此后统一使用 DMG。步骤 8 原文中"按十计数"的设计描述以本修订为准。

## 步骤 9：模式系统与投硬币（用户设计）

日期：2026-09-28　构建：data=57.1 xdata=10 const=279 code=3556，0 错 0 警

### 规格（用户提出 9 条 + 1 条硬原则）

1. 界面分多模式；**计数模式(0)** 最基本，计数值是模式内有效状态；
2. 计数模式中按下 KEY0 → **无条件**进**硬币模式(1)**；
3. 进入即 running=true（硬币在摇）；
4. running=true：LCD 快速固定间隔摇动 "UP"/"DON"（频率凭 LCD 承受度定）；
5. KEY0 松开 → running=false；此后本模式存续期间一切按键一概不理；
6. true→false 时刻屏上的面值即结果；
7. 结果动画：慢闪 3 次（显隐×3，每次"显"伴 2K 蜂鸣）→ 显 5s → 隐 0.5s；
8. 动画全程播完 → 回计数模式，保持其状态；
9. 合理文件分割，不能 main 一包到底。
**硬原则（用户追加，全程生效）：所有动画/流程/按键处理不得阻塞主循环，
时间片定时唤醒是本系统的硬原则。**

### 架构（文件分割）

- `app.c/.h`：唯一全局 `app_mode`；`App_Slice(events)` 每片分发到当前
  模式；`App_SwitchTo()` 切模式并调新模式的 enter 钩子（渲染其面板）。
- `mode_count.c/.h`：模式 0。`count_val`（u16）私有 static；KEY1..6 步进；
  KEY0 按下即切硬币模式。
- `mode_coin.c/.h`：模式 1。相位机 + 片倒计数（u8），状态全部私有。
- `main.c`：boot + 帧循环（采事件 → App_Slice → 心跳打印 → 睡）。

### 接口决策：事件打包为单字节

最初接口 `Slice(key_ev, k0_up)` 在两个模式里各留一个天然未用的参数（count
不用 k0_up、coin 不用 key_ev），C51 报 C280/C275。改为**单字节事件字**：
bit0..6 = 被接受的单键掩码（原样），bit7 = KEY0 松开（`KEY_EV_K0UP`；掩码
本就 ≤0x40，无冲突）。两模式各取所需，参数天然全消费，无 pragma 压警告。

### 时序表（片 = 20ms，全部 u8 定时器）

| 阶段 | 时长 | 片数 |
|------|------|------|
| 摇动每面 | 120ms | 6 |
| 闪-显（伴 2K 蜂鸣） | 400ms | 20 |
| 闪-隐 | 400ms | 20 ×共 3 轮 |
| 长显 | 5s | 250（u8 上限 255 内）|
| 终隐 | 0.5s | 25 |

仪式全长 = 3×0.8 + 5 + 0.5 = **7.9s**（不含摇动时长）。

### 摇动频率依据（120ms/面）

TN 段码屏全响应 ~100ms：翻得更快两面拖影糊成一片（视觉融合），更慢则
不像"摇"。120ms/面（约 8 面/秒）既有摇感、每面仍可辨认。电气上 HT1621
每 120ms 写 6 个 nibble 毫无压力——**瓶颈是视觉不是总线**。可调
`COIN_SHAKE_SLICES`。

### 语义细则

- 结果 = 停止时刻屏上的面（`coin_face` 保持不变，不重算）；
- 起始面恒 "UP"（确定性），随机性来自人手松开时刻；节奏论理论上可博弈，
  休闲设备接受（如需真随机：WKT 时基抖动或 ADC 噪声，留作未来）；
- "UP" 左对齐显示为 "UP "（个位灭），"DON" 占满三位；字形 U/P/D/O/N
  均在 36 字符集内（K/M/V/W/X 才有兜底问题）；
- KEY0 按住跨模式：count 中按下 → 切 coin；coin 中松开 → 停止摇动
  （主 FSM + 松开跟踪器管线天然支持，模式层零特殊处理）；
- 仪式期间按住 KEY0 直到结束回 count：FSM 停在 S1 无新按下事件，k0u
  到达 count 模式被忽略——不会误触发第二次投掷。

### 非阻塞实现要点

- 全部动画 = 相位枚举（SHAKE/BLINK_ON/BLINK_OFF/HOLD_ON/HOLD_OFF）+
  u8 片倒计数，每片 O(1) 判断；流程中无任何 DelayMs（仅 printf 后 1ms
  停止位规矩）；蜂鸣命令 ~0.2ms 非阻塞；模式切换当片即时生效。

### 台架验收

1. 计数模式一切如步骤 8（饱和、进退位、多按拦截）。
2. 按 KEY0：立即开始 "UP "/"DON" 交替（~8 面/秒）。
3. 松 KEY0：停在当前面，串口 `coin UP` 或 `coin DON`；随即 3 次 400ms
   慢闪，每次"显"伴 2K 蜂鸣、每次"隐"静默。
4. 5s 长显 → 0.5s 全灭 → 计数值原样回到屏上。
5. 仪式全程乱按任何键（含 KEY0 按放）：无任何反应。
6. **`ts N` 心跳在仪式期间也每秒一行**——证明主循环从未被阻塞。

## 步骤 12：硬币动画按面分化（用户指令）

日期：2026-09-28　构建：data=58.1 xdata=10 const=258 code=3569，0 错 0 警

### 规格（用户提出）

1. 闪显与鸣叫按结果面分化：UP = 显隐显隐显 / 鸣空鸣空鸣（密）；
   DON = 显隐显 / 鸣空鸣（疏）；两动画总时长基本一致（不必严格）；
2. 动画后固定展示不变（5s）；
3. 固定展示后的空白 0.5s → **0.3s**（15 片）。

### 时序设计（做成精确相等，优于"基本一致"）

| 面 | 相长 | 相数 | 闪显块总长 | 蜂鸣 |
|----|------|------|-----------|------|
| UP | 300ms（15 片）| 5（显隐显隐显）| **1.5s** | 3 声 ×300ms |
| DON | 500ms（25 片）| 3（显隐显）| **1.5s** | 2 声 ×500ms |

仪式全长 = 1.5 + 5 + 0.3 = **6.8s**（两结果等长——时长本身不泄题）。

### 实现要点（mode_coin.c）

- `Coin_BlinkLen()`：按面取相长（300/500ms，显隐同长）；锁面时
  `blink_left` 按面设总相数（5/3），每相到期递减。
- **末相是"显"，直接流入 5s 长显**：最后一个 BLINK_ON 到期时不再
  空隐一拍，直接切 HOLD_ON（面板无变化，无缝衔接）——这正是
  "显隐显隐显 + 固定展示"的字面语义；蜂鸣在末相 ON 到期时已关。
- 相位机结构不变（SHAKE/BLINK_ON/BLINK_OFF/HOLD_ON/HOLD_OFF），
  仅参数按面取值；仍全片驱动零阻塞。

### 台架验收

1. 结果 UP：快节奏三闪三鸣（300ms 相）→ 长显 5s → 灭 0.3s → 回计数。
2. 结果 DON：慢节奏两闪两鸣（500ms 相）→ 同上。
3. 两种结果的仪式时长大体相同（闪显块均 1.5s，可秒表对比）。
4. 其余（进入短鸣、摇动 80ms、忽略按键、ts 心跳）不变。

### 步骤 12 勘误：多鸣/多显一次（台架实锤，同日）

**现象（用户报告）**：UP 和 DON 都多鸣了一次、多显了一次——UP 出现 5 个
"显"、DON 出现 3 个"显"。

**根因**：`blink_left` 初始化用了**总相数**（UP=5、DON=3），但它**只在
"显"到期时递减**——两种计数混用，实际闪显轮数 = 总相数（5/3）而非"显"
的次数（3/2）。

**修复**：`blink_left` 语义固定为**剩余"显"的次数**，初始化改
`UP_BLINK_ONS=3`/`DON_BLINK_ONS=2`，与递减点一致。UP：显隐显隐显（第 3
显流入长显）、3 声；DON：显隐显（第 2 显流入长显）、2 声。块时长仍各
1.5s。构建不变（code=3569）。

**教训**：计数器语义（数什么）必须与其递减点（在哪数）写在一起核对；
设计走查时用"逐相点名"的方式验证到 HOLD 的转移恰好落在最后一个"显"。

## 步骤 13：计数模式 ±100 拒绝语义 + 键反馈鸣叫（用户指令）

日期：2026-09-28　构建：data=61.1 xdata=10 const=258 code=3668，0 错 0 警

### 规格（用户提出）

1. ±100 只操作百位：加减后若越上下限，**直接拒绝**（值不动），不再钳位；
2. 每次加减发声：接受 = 一声短鸣；**拒绝 = 连续超短鸣三次**；
3. 模式切换时必须清除当前模式的鸣叫状态/日程，然后走新模式的进入短鸣。

### 语义统一：拒绝 = "值没动"

- ±100：越界即拒绝（+100 仅当 v≤890；−100 仅当 v≥100），取代原钳位
  （原 50−100→0、950+100→990 的钳位行为废除，均改为拒绝）；
- ±10 保持步进语义，但边界处（990 上 +10、0 上 −10）值不动 → 同样归入
  "拒绝"。
- 于是鸣叫规则天然一致：**值动了 = 接受（一声）；值没动 = 拒绝（三声）**，
  `Count_ApplyKey()` 返回值直接驱动，无第二套判断。

### 键反馈蜂鸣日程（mode_count.c，片驱动）

- 接受：40ms（2 片）单鸣；
- 拒绝：20ms 鸣 / 20ms 空 ×3（共 120ms"哒哒哒"）；
- 实现：ON/GAP 两态小状态机 + u8 计数 `cnt_beep_n`（剩余"鸣"数，含当次），
  每片 `Count_BeepTick()`，与动画同款零阻塞。

### 模式切换时的鸣叫日程清理（用户第 3 点）

机理：切模式后旧模式的 Slice 不再被调用，其日程被"冻结"（永不触发、
无害）；**真正的坑在再进入该模式时残留状态会误关蜂鸣器**（例：接受鸣
剩 1 片时按 KEY0 → 硬币仪式 6.8s → 回计数模式，进入 chirp 100ms 刚响
20ms 就被残留日程关掉）。处理：

- **每个模式的 Enter 钩子清零自己的鸣叫日程**（count：cnt_beep 三变量
  归零；coin：Enter 本就全量重初始化相位机）；
- `App_SwitchTo` 顺序保证正确：先开 chirp + 设 app 定时器，**后**调
  Enter——Enter 只清自己、不碰蜂鸣器，零冲突；
- coin 接管蜂鸣器（锁面闪显）时仍先 `App_BeepCancel()` 作废 app chirp
  定时器（步骤 11 已有）。

### 台架验收

1. 正常步进：每按一次一声短鸣，值变化（含 90→100 进位、100→90 退位）。
2. ±100 拒绝：990/900 上按 +100、0~90 上按 −100 → 值不动 + 三声超短鸣。
3. ±10 边界：990 上 +10、0 上 −10 → 值不动 + 三声超短鸣。
4. 鸣叫中切模式：接受/拒绝鸣响到一半按 KEY0 → 硬币进入短鸣正常（100ms）；
   仪式结束回计数模式，进入短鸣完整 100ms（无残留日程截断）。
5. 串口 `k? v?` 值与屏显一致；拒绝时值重复上一值。

## 步骤 15：待开机模式(2)——深度掉电与长按唤醒（用户设计）

日期：2026-09-29　构建：data=65.1 xdata=10 const=258 code=3896，0 错 0 警
（+4 data：sb_phase/sb_timer/idle_slices；+228 code）

### 规格（用户提出）

- **进入**：无任何操作超过 1 分钟 → 待开机模式(2)：HT1621 停止一切运作、
  蜂鸣关、IO 安全态（VLCD 高阻等）、**不使能 WKT**、使能 INT0（KEY0）、
  进 STOP。进入不蜂鸣——非业务模式。
- **唤醒**：INT0 唤醒后仍在模式(2)，重跑 WKT 时间片，开 1 秒窗口监测
  KEY0 松开：窗口内松开 = 误触 → 回到"无 WKT 的 STOP"，模式不变，
  1 秒计时清除待下次唤醒重算；满 1 秒未松 = 真开机 → 重初始化（IO、
  VLCD 引脚电压、HT1621 系统有效+清数据+关蜂鸣+开 LCD）→ 跳计数模式(0)。
- **架构要求**：进入计数模式时必须妥善屏蔽第一个 KEY0 松开事件（不是
  靠业务上碰巧无害）；全程内存数据保留；进计数模式要蜂鸣。

### 架构实现（mode_standby.c/.h 新模块，零侵入时间片机制）

- **深睡复用唯一的 STOP 点**：`Slice_SleepOneTick()` 的 STOP 不变；
  待机只是把 WKTEN 关掉，同一个 STOP 就变成"只有 INT0 能结束"——
  时间片机制与深睡机制共享一个睡眠点，无第二套睡眠路径。
- **INT0 空 ISR**（`interrupt 0`，向量 0x0003）：只为接住向量干净返回，
  不触碰任何数据；醒来后当片立即 EX0=0/EA=0 恢复"全固件无中断"不变量
  （不变量修订：除待机深睡期间外 EA=0）。
- **SLEEP/AWAIT 两相**（都由帧循环驱动，Enter 不劫持主循环）：
  - SLEEP：Enter 时下电（TONE_OFF→LCD_OFF→SYS_DIS 停振；P1.1 高阻
    （RC 经面板负载放至 0V）；全端口整写准双向安全态——与 SleepForever
    同类的"刻意整写"例外）。醒来当片：disarm INT0、`Timeslice_Init()`
    重开 WKT、置 AWAIT 窗口 50 片；唤醒按键本身不是本模式事件。
  - AWAIT：KEY0 松开优先判（与窗口到期竞态时松开获胜=误触）→ 回
    SLEEP（重新关 WKT、开 INT0）；满 50 片未松 → 重初始化 → 切计数。
- **空闲检测在 app 层**：任何键事件（含 k0up，含被业务忽略但被 FSM
  接受的按下）清零 `idle_slices`（u16，3000 片 = 1 分钟）；仅在非待机
  模式计数；到点 `App_SwitchTo(APP_MODE_STANDBY)`（该模式无 chirp——
  App_SwitchTo 显式豁免，注释言明"house-keeping state"）。
- **重初始化序列**（`Standby_ResumeInit`）：Buttons_Init（键脚输入+
  上拉，P3.2 上拉同时是 INT0 边沿所需）→ HT1621_Init（总线推挽）→
  `VLCD_Reapply()`（重测 VCC 重施加——电池电压可能已变；内含过压检查
  为无，符合"过压只查一次"约定）→ SysInit → TONE_OFF → LcdOn →
  显示缓冲清零 + Render（即"清除数据"：全覆写 SEG0..5 为 0）。
- **首个 KEY0 松开事件的屏蔽**：新增 `Buttons_Key0Disarm()`（清 k0_armed，
  不碰引脚），在切计数模式前调用——待决的长按松开被吞掉，后续正常
  按放不受影响。架构级屏蔽，不依赖计数模式"碰巧忽略 bit7"。
- **内存保留**：STOP 保留全部 RAM，count_val/g_wkt_reload 等原样；
  HT1621 RAM 不保留（SYS_DIS 后无所谓），开机序列显式清零。

### 语义细则与边角

- AWAIT 期间按其他键 → 主 FSM 进 S2，KEY0 在 S2 中松开照样触发 k0up
  （跟踪器设计使然）→ 判为误触回深睡：长按被干扰 = 不算干净长按，回睡。
- 窗口到期与松开同片竞态：松开判先（保守侧，未满 1 秒不算长按）。
- 纯 EMI 假唤醒（无键按住）：无 k0up、1 秒后判"开机"——电池手持设备
  概率极低，接受（如需加固可在唤醒后验证 P3.2 电平，暂不做）。
- 深睡期间主循环每次唤醒跑一圈（n++，心跳 1/250 概率打印一行 ts）——
  开发期噪音，无害。

### 台架验收

1. **自动待机**：静止不操作 1 分钟 → 屏灭、蜂鸣无声、电流降至 µA 级
   （可串 µA 表验证深睡功耗）。
2. **误触**：待机中短按 KEY0（<1 秒松开）→ 屏不亮、无蜂鸣，系统回深睡；
   再次长按仍正常开机。
3. **长按开机**：按住 KEY0 ≥1 秒 → 屏亮（清零后的黑屏瞬间被计数值
   覆盖）+ 进入短鸣一声 + 旧计数值原样显示。
4. **长按的松开不触发任何事**：开机后松开 KEY0，无事件（屏不变、
   无 k0u 类反应）；此后按放 KEY0 正常进硬币模式。
5. **待机前的状态**：待机发生于计数模式或硬币仪式结束后均可；硬币
   仪式期间不会中途待机（仪式最长 6.8s < 1 分钟，且事件清零空闲计数）。
6. **数据保留**：设一个非零计数值 → 待机 → 长按唤醒 → 值不变。

### 抖动审计（用户提问引出，同日）

**用户问题**：唤醒进入待机时按键仍在抖动，1 秒长按判定是否需要开头
一两个时间片的容忍处理？

**唤醒侧结论：不需要。** 论证：醒来后首采样与按键时间锁定（唤醒延迟
µs 级），几乎必见首次闭合（首闭合通常 ≥数百 µs 才首次弹开）→ 当片接受
并武装跟踪器；**下一采样在 20ms 后，已越过整个抖动窗口（≤~10ms）**——
假"误触"需要"武装态下采到高电平"，而抖动窗口内不存在采样点，结构上不
可能。最坏子情形（首采样恰好落在早期弹开缺口，需亚毫秒对齐）仅使接受
推迟一片、阈值等效 +20ms，无感。20ms 采样节拍本身就是容忍。

**释放侧（审计发现的真边角，已加固）**：k0up 可提前触发（采样落进释放
抖动缺口，最多早 ~10ms；普通模式无害）。待机误触路径原本立即重武装
INT0——若释放抖动尾部尚有下降沿会瞬间再唤醒刚进的 STOP：通常只是
20ms 不可见小抖动，但存在极窄的"假唤醒后扫不到闭合 → 1 秒无 k0up →
**假开机**"终态。加固两点（构建 data=65.1 xdata=10 const=258 code=3923）：

1. `Standby_ArmDeepStop()` 先 `IE0=0`：清掉唤醒后残留的 pending 沿，
   杜绝"EX0 一开立刻触发"一类；
2. 新增 **SBS_REARM 宽限相**：误触后先等一片（20ms > 整个释放抖动，
   此时绝无在途下降沿）再重武装 INT0；宽限到期查 P3.2——高电平照常
   深睡，低电平（用户在宽限内真又按下了，该次按下已被扫描接受/武装）
   则开新窗口继续判定，不吞按键。
